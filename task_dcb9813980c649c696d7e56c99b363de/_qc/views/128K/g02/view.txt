### 2. Frame resolution semantics

For each row `i` in a sorted partition, we resolve `[lowerBound, upperBound]`:
- lower offset `lo` (null = unbounded => 0), upper offset `uo` (null = unbounded => numRows).
- If current row's ordering key value `v` is non-null and offsets finite:
  - bound value lower = `v + lo` if ASC else `v - lo`... 

Wait, careful: the spec says:
"For a non-null ordering key value `v` and finite offset `o`, the bound value is `v + o` when ordered ascending (`ASC`) and `v - o` when ordered descending (`DESC`), forming a closed interval `[lowerBound, upperBound]`."

Hmm. Let me think about what this means. In standard SQL RANGE frames:
- `RANGE BETWEEN o PRECEDING AND p FOLLOWING` with ORDER BY k ASC:
  - lower bound value = v - o, upper bound value = v + p.
- With ORDER BY k DESC:
  - lower bound value = v + p, upper bound value = v - o... 

Hmm wait. In DESC ordering, "preceding" means larger values. The frame for ORDER BY k DESC RANGE BETWEEN o PRECEDING AND p FOLLOWING is [v + o, v - p] in value space... no wait:

With DESC ordering, rows are ordered from largest to smallest. "Preceding" rows are rows that come before the current row, i.e., with *larger* values. So `o PRECEDING` in DESC = `v + o` (value larger than v). "Following" = smaller values: `p FOLLOWING` in DESC = `v - p`.

So frame = values in [v + o_PRECEDING ... v - p_FOLLOWING]? Hmm, wait for DESC:
- lower bound (start of frame in row order): rows before current row have larger values. `o PRECEDING` means the frame starts at rows with value >= v + o? no...

Let me think again. ORDER BY k DESC: rows sorted descending by value. Current row at value v. Rows preceding (earlier in sort order) have values >= v (well, >= v in value terms since DESC). RANGE o PRECEDING: frame starts (in row order) at the first row whose value is within o of v, i.e. value >= v + o (for numeric where "within o" means |value - v| <= o). Rows following have values <= v. RANGE p FOLLOWING: frame ends at last row with value >= v - p, i.e. value in [v - p, v + o].

So in both ASC and DESC cases, the frame in *value* space is [v - maxOffsetPreceding, v + maxOffsetFollowing] where offsets are magnitudes... Wait:
