AlvisNLP lacks a globally optimal annotation overlap resolution strategy. Add an optimal maximum-weight non-overlapping selection capability to the core corpus classes and the query expression language.

In the core corpus model, add a new public method `selectMaxWeight` to the existing `Layer` class. It must be an instance method that takes a single `ToDoubleFunction<Annotation>` giving the weight of each annotation and returns a new anonymous `Layer` belonging to the same section, also when the original layer or the selection is empty. This returned layer contains the subset of non-overlapping annotations from the original layer that maximizes the sum of evaluated weights. Two annotations overlap when each of them starts before the other one ends. Spans that merely touch, where one's end equals the other's start, therefore do not overlap, and a zero-length annotation overlaps only the annotations that extend on both sides of its position: it overlaps neither another zero-length annotation nor an annotation that starts or ends at that position. The empty subset, whose total is 0.0, is always a candidate, so an annotation whose weight would lower the total is left out. `Double.NaN` weights must be normalized to 0.0; every other weight value, including positive and negative infinity, contributes to the total under ordinary double arithmetic and must not be clamped or normalized. A subset whose total is not a number, which happens when it mixes positive and negative infinity, is never selected, so an annotation weighted negative infinity never appears in the result. If multiple subsets yield the same maximum total, break ties deterministically by selecting the subset whose member indices (in the original layer's canonical order) are lexicographically least, where a strict prefix compares as less. Totals are compared as plain doubles and nothing but this tie-break decides between equal totals: next to a positive infinite weight, for instance, a finite weight of either sign leaves the total at positive infinity, so the tie-break alone decides whether that annotation is selected. Where rounding would make a total depend on the order in which the weights are added up, any order is acceptable.

Next, expose this capability in the query expression language by adding a new `best-disjoint` operator to the `nav` library. The layer is given either by name, as in `best-disjoint:LAYER` and `best-disjoint:LAYER(WEIGHT)`, or by an expression, as in `best-disjoint(LAYER_EXPR)` and `best-disjoint(LAYER_EXPR, WEIGHT)`, where `LAYER_EXPR` is evaluated as a string against the context element every time the operator is evaluated, and its value is the layer name. All four forms must work both bare and fully qualified with the `nav:` prefix, for example `nav:best-disjoint:LAYER(WEIGHT)` or `nav:best-disjoint(LAYER_EXPR)`.

When evaluated, the operator must return an empty annotation set, without evaluating `WEIGHT`, if the context element cannot be downcast to a section or if the named layer is absent. Otherwise, evaluate the `WEIGHT` sub-expression exactly once for each annotation of the layer, with that annotation as the context element and the value coerced to double whatever the type of the expression, and return the selected annotations in canonical order. If `WEIGHT` is omitted every annotation has the same positive weight, so the largest possible set of non-overlapping annotations is selected, with ties broken as above. The operator's reported evaluation type must be annotations. Its parsed expression must round-trip through serialization in all of these forms: the text produced by `toString()` is written without the `nav:` library prefix, as for the existing layer operators such as `inside` and `overlapping`, so that `nav:best-disjoint:LAYER` is serialized as `best-disjoint:LAYER` and `nav:best-disjoint:LAYER(WEIGHT)` as `best-disjoint:LAYER(WEIGHT)`, and parsing that text again yields an equivalent expression. During name usage collection, register the layer name as a layer when the layer is given by name, and recursively collect from the `LAYER_EXPR` and `WEIGHT` sub-expressions. Finally, document the operator in the standard navigation library documentation XML file: give each of the four forms its own `function-doc` entry, written like the entries of the existing layer operators, that is with nothing but the `first-ftor` and `synopsis` attributes, the synopsis being the form qualified with `nav:` with placeholder names in place of the layer and the weight.
