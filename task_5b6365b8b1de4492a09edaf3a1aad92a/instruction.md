The CAN protocol code generator under `modules/tools/gen_vehicle_protocol` extracts CAN signal definitions from DBC files into intermediate YAML metadata and emits C++ protocol parser and encoder classes. Bit-slice placement, byte ordering, integer sign extension, scaling, boundary clamping, and frame composition are performed via C++ string generation without a standalone executable codec model.

Add an executable bit-exact codec model in module `modules.tools.gen_vehicle_protocol.frame_codec` and re-plumb extraction and emission stages to be model-driven.

`signal_layout(signal: dict, dlc: int) -> SignalLayout` computes per-byte slices for a signal within a `dlc`-byte CAN frame. `signal` is one entry of a protocol's `vars` list (`bit`, `len`, `order`, `is_signed_var`, `precision`, `offset`, `physical_range`, `type`, `name`). Returns an immutable `SignalLayout` with `.slices` (tuple of `(byte_index, start_bit, length)` triples ordered from most-significant to least-significant slice, where `start_bit` is the 0-indexed lowest bit in the byte) and `.bit_width` (`len`). A `SignalLayout` behaves as a value defined by those two attributes alone: rebinding either attribute must fail, two layouts with the same slices and bit width must compare equal and hash equal (whichever signal or frame length they were computed for), and layouts that differ in either must not compare equal.

Slice the signal exactly as the existing protocol emitter already slices it when it lays a signal across frame bytes, for both `motorola` and `intel` values of `order`. If any slice's byte index lies outside `[0, dlc - 1]` or if `signal["len"] > 32`, raise `UnsupportedSignalError` carrying attribute `signal_name`.

The DBC extraction stage (`extract_dbc_meta`) must capture each CAN message's declared payload byte length (`BO_` size in DBC) and store it as integer key `dlc` on every protocol entry in the extracted YAML metadata. Extraction no longer drops signals wider than 32 bits: they are written to the YAML like any other signal, and it is the emission stages that skip and report them.

`FrameCodec(protocol: dict)` is constructed from one protocol entry dictionary (`dlc`, `vars`, `name`, `protocol_type`), exposing `.dlc: int` and `.layout(name: str) -> SignalLayout`. If `vars` contains any signal rejected by `signal_layout`, initialization raises `UnsupportedSignalError` for the first such signal. `.layout(name)` raises `KeyError` for unknown signal names.

- `decode(data: bytes) -> dict[str, bool | int | float]` -- decodes a CAN payload frame into signal values matching C++ generated parse logic, including physical scaling `x * precision + offset`. Return types: `bool` is True when the parsed integer is nonzero; `enum` is that integer as `int`; `int` is the scaled value as `int` (truncated toward zero); `double` is the scaled value as `float`. Raises `ValueError` if `len(data) < self.dlc`.
- `encode(values: dict | None = None, data: bytes | None = None) -> bytes` -- encodes signal values onto an initial `dlc`-byte buffer (default: all zeros). Signals in `vars` are applied in declaration order. Bits outside a signal's own slices keep the value they already had, and where two signals share bits the frame retains the value of the one declared later. Physical values are clamped to the closed interval parsed from `physical_range` (left unchanged when the parsed lower bound is greater than the upper bound) and converted via `(val - offset) / precision` truncated toward zero. Unspecified signals use `False` for `bool`, `0` for `int`, `0.0` for `double`, and for `enum` key `0` if present, otherwise the first entry's key. Raises `KeyError` for unknown signal names and `ValueError` if `len(data) < self.dlc`.
- `quantize(values: dict | None = None) -> dict[str, bool | int | float]` -- computes, for each signal, the physical value that survives `encode` followed by `decode` when that signal is the only one written to an all-zero frame; other signals, including ones that share bits with it, never influence its result. The result has an entry for every signal in `vars`; a signal missing from `values` starts from the same default `encode` uses.

Make code emission model-driven in `gen_protocols.py`, `gen_proto_file.py`, and `gen_vehicle_controller_and_manager.py`. `frame_codec.signal_layout` becomes the one place that decides whether a signal can be emitted: each of these stages asks it about every signal of every protocol, passing the signal and its protocol's `dlc` (directly, or through a helper that calls it), and keeps no width or frame-length rule of its own. A vehicle-specific fork that ships a stricter or a more permissive `signal_layout` then gets every stage emitting and reporting by its rule without touching anything else.

Signals rejected by `signal_layout` must be omitted from generated `.proto` messages (their fields and their enum types), C++ protocol classes (report and control, headers and sources), and controllers, so that a skipped signal's name appears nowhere in the generated files; each emission stage must print the name of every signal it skipped to standard output. What is generated for accepted signals does not change: they keep their `.proto` fields and enum types and their C++ parse and set functions, and for those signals `FrameCodec.decode` and `FrameCodec.encode` return what the generated parse and set functions compute. That agreement is only expected where the generated C++ is itself exact: `precision` and `offset` values the emitter prints without loss (it formats them with `%f`, six decimal places) and raw values that fit the `int32_t` the generated code accumulates into.

In the package `BUILD` file, add a target for `frame_codec.py` and make the targets of the three emission stages depend on it. The change stays inside this package: helper modules added next to `frame_codec.py` are fine, while other build files, CI configuration and the existing tests are left as they are.
